# SentinelPrior - Design Decisions, Limitations, and Future Work

SentinelPrior is a small defensive agent that prioritizes vulnerability-scanner findings. The design separates language-model judgment from security facts. OpenAI Structured Outputs can interpret a natural-language goal and produce a typed operational plan, while NVD, CISA KEV, and FIRST EPSS provide live evidence. Exact scores, catalog membership, and priorities are never generated by the model. A deterministic risk engine combines those sources with user-supplied asset exposure, criticality, and environment. This makes results repeatable, testable, and easy to explain.

The coordinator executes a visible plan, validates the scanner CSV, calls each enrichment tool, applies the priority rules, runs quality checks, and writes Markdown and JSON reports. Each HTTP tool has timeouts and retries. A deliberate EPSS-timeout option demonstrates recovery: after three failed attempts, the agent records the error, marks EPSS unavailable, lowers confidence, and continues with NVD, CISA KEV, and asset context. Missing values remain null rather than being invented. The project also runs without an OpenAI key using a clearly labelled deterministic fallback, enabling reviewers to exercise the entire data and error-handling pipeline.

The assessment inputs are synthetic. Asset names, exposure, criticality, and environment values are fictional, while CVE identifiers are real public identifiers selected to exercise live APIs. The examples do not describe Xiarch, its customers, or any real system. In production, the same normalized schema could be populated from an authorized scanner export.

Important limitations remain. The agent trusts the scanner's CVE mapping and does not prove that a specific asset is exploitable. CISA KEV absence is not proof of safety, and EPSS is only a probability estimate. The scoring rules are a transparent demonstration policy, not an industry standard, and require validation against an organization's risk appetite. Live API availability and changing source data may alter results between runs. Human review is mandatory before remediation.

With more time, I would add scanner-specific import adapters, persistent caching with source-freshness controls, vendor-advisory enrichment, asset-owner workflows, authentication, organization-specific policy configuration, and an evaluation set reviewed by security analysts. I would also measure ranking quality, tool-call reliability, latency, and explanation faithfulness before any production trial.
